# Задание 2. Проверочный лист безопасности бизнес-систем PropDevelopment

## Системы, которые проверяем

| Домен | Системы |
|---|---|
| Продажи | витрина продаж (монолит), `client-tour-app`, `client-mart-app`, `client-crm-app`, `client-mart-estate-app` и их БД |
| ЖКУ | витрина ЖКУ, мобильное приложение собственника, `tenant-core-app` и его БД, CRM собственников и её БД |
| Финансы | `accountant-service-1`, его БД, служба каталогов |
| Данные | хранилище, BI, отчётность |
| Внешние | API управляющих компаний (партнёры), интеграции с госорганами |

## Какие разделы шаблона включил и почему

За основу взят шаблон из шестого урока. Разделы выбирал по двум заявленным проблемам компании — нарушенный контроль данных и небезопасные API партнёров — и по четырём потребностям бизнеса (удовлетворённость клиентов, развитие BI/ML/AI, реакция на инцидент у конкурента, соответствие законодательству).

| Раздел шаблона | Включён | Почему |
|---|---|---|
| **I. Управление доступом** | да | Здесь лежат обе подтверждённые проблемы: клиент видит чужие ФИО, партнёр одной УК читает данные другой. Без MFA, минимальных привилегий, журналов доступа и контроля внешнего доступа аудит бессмысленен. |
| **II. Безопасность данных** | да | Потоки данных не контролируются системно, точек регистрации клиента несколько, ограничений со стороны систем хранения нет. Без классификации, шифрования, резервного копирования, Data Governance и контроля целостности нельзя закрыть потребность развивать BI/ML/AI и соответствовать 152-ФЗ. |
| **III. Защита инфраструктуры** | да | Внешний доступ идёт через firewall, сервисы в Kubernetes и гибриде. Нужно проверить сегментацию, фильтрацию между сегментами, периметр и уязвимости — иначе партнёрские API и кластер остаются открытыми точками входа. |
| **IV. Управление инцидентами** | да | У конкурента уже была публичная утечка; у PropDevelopment нет уверенности, что инцидент заметят и разберут. SIEM, оповещения, план реагирования и аудит политик — прямой ответ на эту потребность бизнеса. |
| **V.1. Общие вопросы** | частично | Мобильное приложение собственника и гибридное/облачное размещение делают MDM, VPN и контроль резервных копий в облаке релевантными. Полный блок «незарегистрированных устройств» оставляю, но с пометкой, где данных мало. |
| **V.2. Оборудование и физическая безопасность** | нет | Физическая охрана ЦОД и СКУД важны, но к двум заявленным проблемам (контроль данных и API партнёров) не относятся. Раздутый лист снижает шанс, что аудит доведут до конца. |

## Обозначения в колонке «Да/нет»

- **Да** — требование выполняется по описанию компании.
- **Нет** — требование не выполняется; это следует из описания.
- **Частично** — что-то сделано, но не системно.
- **Нет данных** — в описании недостаточно сведений, аудитор выясняет на месте.
